# billing-meter — Plan

## Goal

Build a production-minded Python REST API (**billing-meter**) that ingests usage events, aggregates them per customer (with time windows), returns costed summaries, and serves a structured JSON invoice for each completed billing month. Frontend = prettified JSON responses for now.

## Stack

- **Python 3.14** (available locally)
- **FastAPI + Uvicorn** — thin HTTP layer
- **SQLite** (stdlib `sqlite3`, WAL, `synchronous=FULL`, busy_timeout) — durable event store; no ORM unless pain forces it
- **Pydantic** — response models (request bodies are parsed with a decimal-preserving JSON parser, see Event processing)
- **pytest** — tests
- **uv** — deps / lock / venv (preferred)
- **requirements.txt** — pip-friendly export; regenerated by pre-commit `freeze` + `make freeze` / `make local-setup`
- **black** — formatting
- **ruff** — lint
- **pre-commit** — single entry point for all lint/format checks (local hooks, `make lint`, CI)
- **GitHub Actions** — remote lint + test with caching
- **Makefile** — `local-setup` plus day-to-day commands

Keep third-party deps light: FastAPI / uvicorn / pytest / httpx (+ black, ruff, pre-commit as dev tools). No Redis/Postgres/Celery, no PDF library in v1.

## Locked product decisions

| Topic | Decision |
|-------|----------|
| Project name | **billing-meter** (package: `billing_meter`) |
| Timezone | **UTC** for all DB/backend ops; local TZ display is future frontend work |
| Window bounds | `from`/`to` and resolved `today`/`month` are **inclusive on both ends** |
| Quantity | JSON number, **> 0** and **≤ 1,000,000,000**, at most **6 decimal places** (trailing zeros don't count). Parsed, stored and summed as an **exact decimal**, never binary float. |
| `resource_type` | Non-empty, ≤ 64 chars, `^[A-Za-z][A-Za-z0-9_\-]*$`, case-sensitive |
| `customer_id`, `event_id` | ≤ 128 chars, `^[A-Za-z0-9][A-Za-z0-9_\-.:]*$` (starts with a letter or digit; no whitespace, no `/`) |
| `event_id` scope | Unique across **all** customers |
| Required fields | `event_id`, `customer_id`, `resource_type`, `quantity`, `timestamp` — any missing → batch rejected |
| Timestamps | Strict RFC 3339: `YYYY-MM-DDTHH:MM:SS[.f{1,6}](Z\|±HH:MM)`, checked with a regex before parsing (Python's `fromisoformat` alone silently truncates a 7th fractional digit and accepts week dates, `24:00` and compact forms). Normalized to UTC; years 0001–9998 after conversion. **Future-dated rejected** beyond a configurable skew tolerance (default **5 minutes** ahead of server UTC). Past timestamps are only limited by closed months (below). |
| Batch failure | **Reject entire batch**; no partial accept |
| Atomicity | Every mutating request is **one transaction** — commit all or rollback |
| Empty batch | **Rejected** (`400`) |
| Batch size | Default cap **1,000** events, configurable; over the cap → `400` |
| Same `event_id` twice in one batch, **identical** payload | Collapsed: first copy is processed, later copies are reported `unchanged` |
| Same `event_id` twice in one batch, **different** payload | **Reject entire batch** (`400`) — ambiguous request |
| Same `event_id` already stored, identical payload | `unchanged` — success, even if its month is closed |
| Same `event_id` already stored, different payload | **`409`** — stored events are immutable; no corrections. Clients send a new `event_id` instead |
| Closed months | A UTC month is closed when `now ≥ start of the next month + grace` (grace default **5 minutes**, configurable). Closure is purely time-based and the same for every customer. A **new** event whose timestamp falls in a closed month rejects the batch with `409`. |
| Batch HTTP status | **`201`** every event `created`; **`200`** success with at least one `unchanged`; **`400`** validation failure; **`409`** conflict with stored state (different payload for a stored `event_id`, or a new event in a closed month); **`503`** + `Retry-After: 1` if the database stays locked past `busy_timeout` |
| Unknown event fields | Ignored, and not part of the "identical" comparison |
| Unknown customer | No customer registry: usage/summary return `200` with empty totals; a closed month returns a zero-total invoice |
| Response numbers | Quantities, unit prices and money are **decimal strings** (e.g. `"10.500000"`, `"12.34"`), never JSON floats. All responses go through Pydantic models (which serialize `Decimal` as strings); returning plain dicts would let FastAPI's encoder turn `Decimal` into float |
| Storage | **SQLite** for v1; single-worker `make run` recommended |
| Pricing | **Deterministic PoC** — no client-supplied prices. Unit price per `resource_type` computed directly from a SHA-256 digest of its name (same input → same price, across calls, restarts and Python versions). Used by **both** summary and invoice. |
| Invoice format | **Structured JSON only**; PDF deferred |
| Billing period | **UTC calendar month** (`YYYY-MM`) |
| Invoice readiness | Ready once the month is closed. Not ready → **`404`** with a `Retry-After` header: seconds until it closes, rounded **up**, minimum 1 |
| Invoice storage | **Not stored.** Computed on request; immutable events + closed months + deterministic pricing make repeated fetches identical |

## API Surface (v1)

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/v1/events` | Ingest one or more events (batch). Idempotent by `event_id`. |
| `GET` | `/v1/customers/{customer_id}/usage` | Totals by resource type for a time window. |
| `GET` | `/v1/customers/{customer_id}/summary` | Usage + pricing table + computed costs for a time window. |
| `GET` | `/v1/customers/{customer_id}/invoices/{period}` | JSON invoice for a closed UTC month (`period` = `YYYY-MM`). |
| `GET` | `/health` | Liveness + DB reachability (`SELECT 1`) |

`customer_id` in paths follows the same format rule as in events; an invalid one → `400`.

### Event payload (batch)

```json
{
  "events": [
    {
      "event_id": "evt_123",
      "customer_id": "cust_abc",
      "resource_type": "api_calls",
      "quantity": 10.5,
      "timestamp": "2026-10-08T12:00:00Z"
    }
  ]
}
```

- Persist (commit) before acknowledging.
- Response lists a per-event outcome by index: `created` / `unchanged`.

### Event processing

1. **Parse** the raw body with `json.loads(parse_float=Decimal, parse_constant=<reject>)` so numbers never pass through binary float and `NaN` / `Infinity` are refused (they bypass `parse_float`). Any parse failure — `JSONDecodeError`, `ValueError` from an integer literal over Python's digit limit, `RecursionError` from deeply nested input — is a `400`, never a `500`. Booleans are rejected where numbers are expected; strings are rejected for `quantity`. The endpoint documents its body schema via `openapi_extra`, since it doesn't use a Pydantic request model.
2. **Validate** (no DB access). Collect *all* errors, then reject with `400` if any:

   | Check | Status |
   |-------|--------|
   | Malformed JSON / missing required field / wrong type | `400` |
   | Empty `events`, or more than the batch cap | `400` |
   | `quantity` ≤ 0, > 1,000,000,000, `NaN`/`Infinity`, or more than 6 decimal places | `400` |
   | `resource_type` / `customer_id` / `event_id` fail their format rules | `400` |
   | Timestamp fails the strict RFC 3339 pattern, or out of range once converted to UTC | `400` |
   | Timestamp > server UTC now + skew tolerance | `400` |
   | Same `event_id` twice in the batch with different payloads (compared on normalized values, see "Identical" below) | `400` |

3. **Collapse** identical in-batch duplicates (later copies → `unchanged`).
4. **`BEGIN IMMEDIATE`** (takes the write lock; if it can't within `busy_timeout`, respond `503`), then read the clock. "Now" for closure checks is always read *after* the lock is held, so a write that waited on the lock can't slip into a month that closed meanwhile.
5. Load stored rows for the batch's `event_id`s (in chunks of 500, to stay under SQLite's parameter limit) and classify each event:
   - not stored → candidate `created`
   - stored and identical → `unchanged` (no further checks)
   - stored and different → conflict
6. **Check conflicts.** Collect all, then roll back with `409` if any:
   - different payload for a stored `event_id`
   - `created` event whose timestamp is in a closed month
7. Insert `created` rows, commit, then respond.

"Identical" compares normalized values — both within a batch and against stored rows: same `customer_id`, `resource_type`, quantity as an exact decimal (`10.5` == `10.50`), and the same UTC instant (so `+05:30` vs `Z` for one instant is identical). Unknown extra fields are ignored.

FastAPI's default `422` for request validation is overridden to `400`. Error bodies list every offending event index and reason.

### Time windows (query params)

- Exactly one of: `window=today|month`, **or** both `from` + `to` (same strict RFC 3339 format as event timestamps).
- `400` for: no window params, `window` combined with `from`/`to`, only one of `from`/`to`, `from` > `to`, a value failing the strict format or out of range once converted to UTC, or an unknown `window` value. `from == to` is valid (a single instant).
- `today` / `month` resolved in **UTC**.
- Bounds **inclusive** on both start and end.
- Bound construction (UTC): `today` = `[today 00:00:00.000000Z, today 23:59:59.999999Z]`; `month` = `[first day 00:00:00.000000Z, last day 23:59:59.999999Z]`.
- Aggregation filters on event `timestamp`, not ingest time — out-of-order / skew-safe.
- `+` in an offset must be URL-encoded as `%2B` in query strings (documented in the README).

### Pricing (deterministic PoC)

- Clients never send prices.
- `unit_price(resource_type)` = `int.from_bytes(sha256(name.encode()).digest()[:8], "big") % 100 + 1` ten-thousandths of a dollar, i.e. **$0.0001–$0.0100 per unit**. No `random` module: its sequence isn't guaranteed across Python versions, and invoices aren't stored.
- Money handled as `Decimal`. Line cost = **aggregated quantity for the resource** × unit price, rounded to cents (half-up). Total = sum of the rounded line costs. Summary and invoice use the same function, so they always agree for the same range.
- Summary and invoice responses both include the **pricing table** used.

### Invoices

`GET /v1/customers/{customer_id}/invoices/{period}`

- Customers poll this endpoint; there is no "generate" action.
- Ready once the month is closed. Current or future month → `404` + `Retry-After`. Bad `period` format, or a year outside 0001–9998 → `400`. An invalid `customer_id` → `400`.
- The read runs inside `BEGIN IMMEDIATE`, so it can't interleave with an ingest transaction that started just before closure: either that write commits first and is included, or it sees the month closed and gets `409`.
- Response (JSON): deterministic `invoice_id` (`INV-{customer_id}-{YYYY-MM}`; the fixed-width suffix keeps it unambiguous), customer, period start/end, line items (resource type, quantity, unit price, cost), pricing table, total, currency placeholder.
- A closed month with no usage (including unknown customers) returns a valid zero-total invoice.
- Repeated fetches return identical content: stored events never change, closed months accept no new events, and pricing is deterministic. (Assumes the server clock doesn't move backwards across a month boundary.)

## Persistence

Single SQLite DB file (path via env, default `./data/billing-meter.db`; the directory is created on startup).

- Connection per request (FastAPI runs sync handlers in a threadpool).
- `autocommit=True` on the connection; transactions are controlled only with explicit SQL (`BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`). In this mode `conn.commit()` / `conn.rollback()` are no-ops, so they must not be relied on.
- `sqlite3.OperationalError: database is locked` after `busy_timeout` → `503` with `Retry-After: 1`.
- `PRAGMA journal_mode=WAL`, `PRAGMA synchronous=FULL` (an acknowledged event survives power loss), `PRAGMA busy_timeout=5000`.

```text
events(
  event_id TEXT PRIMARY KEY,
  customer_id TEXT NOT NULL,
  resource_type TEXT NOT NULL,
  quantity_micros INTEGER NOT NULL CHECK (quantity_micros > 0),  -- quantity × 1,000,000
  timestamp TEXT NOT NULL,  -- UTC, fixed width: YYYY-MM-DDTHH:MM:SS.ffffffZ
  ingested_at TEXT NOT NULL
)
```

Indexes: `(customer_id, timestamp)`.

- Timestamps are always written with an explicit 6-digit microsecond format (not `isoformat()`, which drops zero microseconds), so string comparison equals time comparison.
- Integer `SUM` over `quantity_micros` is exact and independent of row order. With the 1e9 cap (1e15 micros per event), overflow needs ~9,200 max-size events for one resource in one window; if SQLite raises integer overflow, fall back to summing rows in Python (unbounded ints) rather than failing.

No invoice table — invoices are derived.

## Testing (required)

- **Required by the question:** a test proving out-of-order arrival produces correct totals (events ingested in shuffled timestamp order, across multiple batches, give exactly the same totals as in-order ingestion).
- Unit: window resolution, aggregation math, decimal quantity parsing (incl. a large value with 7 decimals, which a float parse would silently round), deterministic pricing (stable across calls / processes), cent rounding, closure rule at exactly `start of next month + grace` (closed) and one microsecond before (open).
- Validation: negative, zero and over-cap quantity, `NaN`/`Infinity`, > 6 decimals, booleans/strings as quantity, each missing required field, future timestamp beyond tolerance (rejected) vs within (accepted), naive timestamp, 7 fractional digits, week-date / `24:00` / compact timestamp forms, out-of-range timestamp, bad formats incl. `.`/`..` ids, over-cap batch, malformed JSON, huge integer literal, deeply nested JSON — each returns `400` (never `500`), writes nothing, and the error body lists every problem.
- Durability: ingest, close and reopen the database file, and confirm every acknowledged event is still there.
- `/health`: `200` with a working database, failure status when the database can't be opened.
- Idempotency: identical in-batch duplicate → `200` with one stored row; differing in-batch duplicate → `400`; identical replay → `200`; identical replay into a closed month → `200`; different payload for a stored `event_id` → `409`; two concurrent batches with the same new `event_id` → one stored row, both succeed.
- Atomicity: a failure mid-transaction rolls back every event in the batch.
- API (TestClient): `201`/`200`/`400`/`409` rules, window param errors, `from == to`, today/month/custom inclusive range, offset timestamps that cross a UTC month boundary, unknown customer → empty totals, decimal-string response format, summary includes pricing table.
- Invoices: current month → `404` + `Retry-After` (≥ 1, rounded up), just before vs at the closure instant, bad period / out-of-range year / invalid customer → `400`, closed-month totals match summary for the same range, zero-usage invoice, repeated fetch identical, shuffled ingestion order gives an identical invoice, new event into a closed month → `409`.
- Lock contention: a write blocked past `busy_timeout` → `503` + `Retry-After`.
- Temp SQLite per test (fixture) + pinned clock.
